# Carolina Heating Service — Next.js rebuild of carolinaheating.com

This is a **high-fidelity port** of the live WordPress site (NearU base theme + CHS child theme). The goal is visual and structural parity with the original, so the architecture is built around the original theme's real CSS and DOM rather than a re-interpretation.

This is also brand **#1 of 23** NearU family-of-brands sites. Content (nav, business info, pages, images, testimonials, certifications) lives in a **shared Supabase project**, scoped per-brand by a `site_id`/`SITE_SLUG`. Theme code (this repo's `src/`) is meant to be reused as-is for other brands running the same NearU/CHS theme — only the Supabase rows differ.

## How the site is assembled

1. **Theme CSS (`src/app/theme.css`)** — generated by `node scripts/build-theme-css.mjs`. It fetches every page of the live site with `?nowprocket=1` (bypasses WP Rocket's minify/"remove unused CSS") and concatenates the ORIGINAL stylesheets in WordPress' exact enqueue order: WP core block styles → theme.json presets (`--wp--preset-*`) → Simple Banner plugin → `nearu-base/dist/css/style.css` → `chs/style.css` → inline @font-face/site-title → Customizer CSS → lite-youtube → promotions block. Font URLs are rewritten to `/fonts/`. **Never hand-edit theme.css**; re-run the script.
2. **Global chrome (React, Supabase-backed)** — `src/components/Header.tsx`, `Footer.tsx`, `SimpleBanner.tsx` reproduce the original `#masthead`/`#colophon`/`.simple-banner` markup and class names 1:1. `Footer`/`SimpleBanner` and most `blocks/*` components are `async` server components that call `getSite()` (`src/lib/db/site.ts`) directly; `Header` is a client component that receives `site: SiteData` as a prop from `layout.tsx`. `Header.tsx` ports the behavior of the theme's `navigation.js` (mobile `.toggled` drawer, `data-header-nav-expanded` on `<html>`, `aria-expanded`-driven sub-menus). The SVG icon sprite (`src/lib/iconSprite.ts`, 51 icons) is inlined right after `<body>` exactly as the theme does; use `<Icon name="..."/>`.
3. **Homepage (`src/app/page.tsx`)** — hand-built in React, block-for-block against the original DOM, using the shared block components in `src/components/blocks/` (ServicesList, IconList, ImageStack, OurCommunity, MaintenanceFinancing, Certifications/LogoCarousel, GoogleReviews, YouTubeEmbed, Elevated). It fetches `getSite()` + `getPage("/")` from Supabase; the homepage's jsonb `data` column (shape: `src/lib/db/homePageData.ts`) holds copy, and `inline_css` holds WordPress' per-page layout CSS.
4. **Every other page (`src/app/[...slug]/page.tsx`)** — served from the `pages` table via `getPage(routePath)`/`getAllPagePaths()` (`src/lib/db/pages.ts`), `dynamicParams = true` + `revalidate = 3600` (ISR: new/edited Supabase rows show up within an hour automatically, or instantly via `POST /api/revalidate`). Each row holds the page's `<main>` inner HTML (cleaned: lazy-load placeholders removed, absolute links made root-relative, schedule buttons routed to `/bookings`, images pointing at Supabase Storage), plus `title`, `description`, `og_image_path`, and `inline_css` (WordPress' per-page `core-block-supports-inline-css` — `.wp-container-*`/`.wp-elements-*` rules whose hashes are unique per page, so they are emitted per page like WordPress does, not merged globally). `src/components/ThemeBehaviors.tsx` ports the theme's `carousel.js`, logo-carousel arrows, and lite-youtube click-to-play onto this server-rendered HTML.
5. **Images / fonts** — images live in Supabase Storage (public bucket `site-media`, path `<site_slug>/images/...`, resolved via `mediaUrl()` in `src/lib/supabase/server.ts`); fonts remain self-hosted in `public/fonts/`. Nothing hotlinks to the old site.
   - **Performance**: `next.config.ts` allows `next/image` to optimize the Supabase Storage hostname (computed from `SUPABASE_URL`). Every hand-built JSX `<img>` (Header/Footer logo, homepage hero/imagestack/promise images, `MaintenanceFinancing`, `OurCommunity`, `LogoCarousel`) uses `next/image` instead — this resizes + converts to a modern format + serves from Vercel's edge cache (e.g. the ~540KB header logo PNG becomes a ~17KB response at typical display size). The migration script also sets a 1-year `Cache-Control` on every Storage upload (`scripts/db/migrate-to-supabase.mjs`'s `uploadImages()`).
   - **Known gap**: the 106 mirrored pages' images are raw `<img>` tags inside `dangerouslySetInnerHTML`-injected WordPress HTML (`pages.html`), so they can't go through `next/image` without parsing/rewriting that HTML into React elements — a bigger, separate project. They still benefit from the long Storage `Cache-Control` and from `layout.tsx`'s `<link rel="preconnect">` to the Supabase Storage origin, but not from resizing/format conversion. If this becomes a real bottleneck, the fix is either (a) post-process `content/html/*.json` at migration time to inject `srcset`/explicit dimensions, or (b) parse the HTML into React and swap `<img>` for `<Image>` at render time.
   - **Every `next/image` usage sets `placeholder="blur"` + `blurDataURL={shimmerDataUrl(w, h)}`** (`src/lib/imagePlaceholder.ts`) — a generic shimmer, not a real preview of the image (we don't have per-image blurhash data). This exists because Next.js's route prefetch on `<Link>` hover/viewport doesn't prefetch the actual (remote, on-demand-optimized) image bytes, so there's a real gap between a client-side navigation landing and the destination page's image finishing its fetch — worse on a cold Vercel image-optimizer cache. The shimmer fills that gap instead of leaving blank space. Add this to any new `next/image` usage.

## Data layer (Supabase)

- **Schema**: `supabase/migrations/0001_init.sql` (core tables) + `0002_integrations.sql` (nullable third-party IDs on `sites`) — `sites`, `nav_items`, `service_categories`, `sub_services`, `locations`, `pages` (generic jsonb+html for mirrored/custom pages), `certifications`, `testimonials`, `redirects`, `media_assets`. RLS enabled everywhere, no permissive policies — all access is server-side via the `service_role` key (`src/lib/supabase/server.ts`, marked `server-only`). See `supabase/README.md` for full setup/onboarding steps for additional brands.
- **Query layer**: `src/lib/db/site.ts` (`getSite()`, React-`cache()`-wrapped) and `src/lib/db/pages.ts` (`getPage()`, `getAllPagePaths()`, `getSitemapEntries()`, `getSiteId()`). `src/lib/site.ts` now only exports TypeScript types (`SiteData`, etc.) — no runtime data. Never import a hardcoded site object; always go through `getSite()`.
- **Env vars** (see `.env.example`): `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SITE_SLUG` (this brand's row in `sites.slug`), `REVALIDATE_SECRET`. `middleware.ts` (DB-driven redirects) reads `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`/`SITE_SLUG` too — these must also be set as **Edge**-available env vars in Vercel (all Vercel env vars are available to Middleware by default, no extra config needed).
- **Seeding/re-syncing content**: local files under `content/` (`site.json`, `pages/home.json`, `pages/home-inline.css`, `html/*.json`) are the source-of-truth staging area fed into Supabase by `node scripts/db/migrate-to-supabase.mjs` (`npm run db:migrate`, or `npm run db:migrate:content-only` to skip re-uploading images). The script is idempotent — safe to re-run after editing any of those files. It also derives a **thin index** into `locations` (pages matching `/<city>-hvac-plumbing-electrical-generators`) and `sub_services` (pages matching `/services/<category>/<sub-service>`) purely from those same mirrored-page paths — see "Locations & sub-services" below.
- **Editing content going forward**: either (a) edit the local `content/*` files and re-run `npm run db:migrate`, or (b) write directly to Supabase in a one-off script using the same pattern as `scripts/db/migrate-to-supabase.mjs`. After any edit, hit `POST /api/revalidate?secret=$REVALIDATE_SECRET&path=/some-path` for an instant refresh instead of waiting up to an hour for ISR.
- **Re-sync a page from the live WordPress site** (still useful as the first step before migrating) → `node scripts/extract-pages.mjs https://carolinaheating.com/<path>/`, then `npm run db:migrate`. Re-sync everything: `node scripts/extract-pages.mjs` (uses `scripts/pages.txt`) then `npm run db:migrate`.
- **Redirects** are DB-driven: the `redirects` table (seeded from `content/site.json`'s `"redirects"` array) is read by `middleware.ts` on every request (5-minute in-memory cache, falls back to stale cache or no-op if Supabase is unreachable). Add a redirect by adding a row to `content/site.json`'s `redirects` array + `npm run db:migrate`, or by inserting directly into the `redirects` table — either way it takes effect within 5 minutes with **no redeploy**. `next.config.ts` deliberately has no `redirects()` — don't add hardcoded ones there, they'd be a second, conflicting source of truth.

### Locations & sub-services (thin index)

`locations` and `sub_services` have rich structured columns (`service_groups`, `faqs`, `since_categories`, etc.) designed for real field-level editing, but populating those requires actually parsing ~57 pages of freeform WordPress HTML into structured data — high effort, high risk of content drift from the live site. For now the migration script only inserts a **thin index** (slug/title/href/image, derived by pattern-matching `content/html/*.json` paths) into these tables for cross-linking/sitemap purposes. **The pages themselves still render from the generic `pages` table's mirrored HTML** (via `[...slug]/page.tsx`), not from these tables. If a brand later needs true structured editing of location/sub-service pages, that's a deliberate, separate project: extract each page's content into the structured columns and switch the relevant routes to render from `locations`/`sub_services` instead of `pages`.

## Third-party integrations

All of these are **nullable columns on `sites`** and render nothing when unset — safe by default for prototypes/staging. Fill in via Supabase (or `content/site.json`'s `business` object, re-run `npm run db:migrate`) when a brand actually goes live:

- **ServiceTitan scheduler** (`scheduler_id`, `scheduler_api_key`) — `src/app/layout.tsx` conditionally renders the real `embed.scheduler.servicetitan.com/scheduler-v1.js` embed. `.se-widget-button` elements (see `Cta.tsx`'s `schedule` prop, `Header.tsx`) get a real click → `_scheduler.show(...)` via a delegated listener in `ThemeBehaviors.tsx` (reads the id from `<body data-scheduler-id>`), falling back to their normal href (the `/bookings` mirrored page) if the widget/id isn't configured.
- **Google Tag Manager** (`gtm_id`) and **Tealium** (`tealium_src`) — raw snippets in `layout.tsx` (not `@next/third-parties/google`, which currently only ships versions tracking Next's 16.4 canary line — revisit once it has a stable release matching our Next version).
- **Cookie consent banner** (`src/components/CookieConsent.tsx`) — always renders (no third-party dependency; it's the NearU theme's own `cookie-consent.js` custom element, faithfully ported as a client component using the exact same tag/classes so theme.css's `cookie-consent[module-type=banner]` rules apply unchanged). Cookie name/expiry (`cookieConsent_acknowledged`, 7 days) matches the original.
- **Structured data (JSON-LD)** — `layout.tsx` emits site-wide Organization/LocalBusiness/WebSite (matching the live site's AIOSEO `@graph`); `src/lib/schema.ts`'s `buildPageSchema()` adds per-page WebPage/BreadcrumbList, used by both `page.tsx` and `[...slug]/page.tsx`.
- **Chat widget** ("Text us" bubble) — still not ported; no embed code/account id captured yet.
- The generator landing page's Mailchimp form posts directly to Mailchimp and works without extra JS.

## SEO infrastructure

- `src/app/sitemap.ts` — one flat sitemap generated from `getSitemapEntries()` (every `pages` row for this site). Replaces the live site's 3-file AIOSEO sitemap index; fine for a single-brand site well under the 50k-URL limit.
- `src/app/robots.ts` — allows all, points at `/sitemap.xml`.
- `src/app/not-found.tsx` — themed 404 (uses `getSite()` for phone number + top service links).
- `src/app/error.tsx` — themed error boundary for errors in pages/children of the root layout. Must be a Client Component (Next.js requirement) so it can't call `getSite()`.
- `src/app/global-error.tsx` — last-resort boundary for errors in the **root layout itself** (e.g. Supabase totally unreachable during `getSite()` in `layout.tsx`) — `error.tsx` can't catch those since a layout's errors can only be caught by replacing the whole document. Deliberately plain/inline-styled, no theme.css dependency.

## Do not

- Do not add Tailwind or other CSS frameworks — the theme CSS ships its own reset and grid primitives and they conflict.
- Do not hotlink images/fonts to carolinaheating.com — Cloudflare bot protection on that origin blocks Vercel's image optimizer.
- Do not import `src/lib/supabase/server.ts` (or anything from `src/lib/db/*`) into a `"use client"` file — it's `server-only` and uses the service-role key on purpose. Client components that need site data should receive it as props from a server component ancestor (see `Header.tsx` / `GoogleReviews.tsx` + `GoogleReviewsSection.tsx` for the pattern).
- Do not hardcode this brand's business info/copy/nav in component code — it belongs in Supabase (`sites`/`nav_items`/etc.) so the same components work for all 23 brands. Add new fields to the schema + `SiteData` type instead of hardcoding.
- Do not add a hardcoded `redirects()` to `next.config.ts` — see "Redirects" above.
- Do not render a real custom element tag in JSX (e.g. `<cookie-consent>`, `<lite-youtube>`) without adding it to `src/types/custom-elements.d.ts` first — React 19 doesn't type-check unknown hyphenated tags automatically, and the augmentation must target `declare module "react" { namespace JSX {...} }`, **not** `declare global { namespace JSX {...} }` (the latter silently fails to merge under `"jsx": "react-jsx"`).
