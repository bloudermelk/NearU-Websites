# @nearu/site-kit — the shared codebase behind every NearU brand website

This package is imported by every brand site folder in the repo (`carolina-heating/`, `2nd-wind/`, … one per brand, 23 planned). A brand folder is a complete, independently deployable Next.js app whose `app/` routes are one-line re-exports of `src/routes/*` here, plus that brand's own `app/theme.css`, `public/fonts/`, favicon and `content/` (mirrored WordPress pages/images + `site.json`). Each brand is a **high-fidelity port** of its live WordPress site (all brands run the same NearU base theme + a per-brand child theme), so the architecture is built around the original theme's real CSS and DOM rather than a re-interpretation.

**Where things live** (repo root = `NearU-Websites/`):
- `packages/site-kit/src/` — components, data layer (`lib/db`), route implementations (`routes/`), middleware, `globals.css`. **Zero brand-specific code allowed here** — if a brand needs something others don't, it becomes a nullable column / `site.json` field, never `if (slug === …)`.
- `packages/site-kit/scripts/` — content pipeline, exposed to brand folders as npm bins (`nearu-*`) and wired as each brand's `npm run content:*` / `db:*` scripts. Scripts always run **from inside a brand folder** and resolve the brand from `./content/site.json` (`"slug"`).
- `<brand>/` — `next.config.ts` (`createSiteConfig({ siteSlug })` bakes `SITE_SLUG` into the bundle), thin `app/` routes (segment configs like `revalidate`/`dynamicParams`/middleware `config` MUST be literals there — Next.js won't accept re-exported ones), `app/theme.css`, `public/fonts/`, `app/icon.png|favicon.ico`, `content/`, `middleware.ts`, `.env.local`.
- `supabase/` — the ONE shared database (`schema.sql` full, `migrations/` incremental, `README.md` tenancy model + onboarding).
- Each brand = one Vercel project on this repo (Root Directory = the brand folder). Env vars are identical for all brands (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `REVALIDATE_SECRET`) — no per-brand env vars.

**Data model**: `companies` (NearU, 1 row: cookie notice, legal links, careers ATS — anything identical across brands) → `sites` (one per brand) → everything else keyed by `site_id`. `getSite()` returns `{ company, business, theme, nav, footer, serviceCategories, certifications, testimonials }`.

## How the site is assembled

1. **Theme CSS** — `npm run content:theme-css` (in a brand folder) writes that brand's `app/theme.css` and mirrors fonts to `public/fonts/`. It fetches every page of that brand's live site with `?nowprocket=1` (bypasses WP Rocket's minify/"remove unused CSS") and concatenates the ORIGINAL stylesheets in WordPress' exact enqueue order: WP core block styles → theme.json presets (`--wp--preset-*`) → Simple Banner plugin → `nearu-base/dist/css/style.css` → `<child-theme>/style.css` → inline @font-face/site-title → Customizer CSS → lite-youtube → promotions block. Font URLs are rewritten to `/fonts/`. **Never hand-edit theme.css**; re-run the script.
2. **Global chrome (React, Supabase-backed)** — `components/Header.tsx`, `Footer.tsx`, `SimpleBanner.tsx` reproduce the original `#masthead`/`#colophon`/`.simple-banner` markup and class names 1:1. `Footer`/`SimpleBanner` and most `blocks/*` components are `async` server components that call `getSite()` (`lib/db/site.ts`) directly; `Header` is a client component that receives `site: SiteData` as a prop from `routes/layout.tsx`. `Header.tsx` ports the behavior of the theme's `navigation.js` (mobile `.toggled` drawer, `data-header-nav-expanded` on `<html>`, `aria-expanded`-driven sub-menus). The SVG icon sprite (`lib/iconSprite.ts`, 51 icons) is inlined right after `<body>` exactly as the theme does; use `<Icon name="..."/>`.
3. **Homepage (`routes/home.tsx`)** — polymorphic on the `/` row's `page_type`. **Default for every brand: `mirrored`** — the live homepage is extracted like any other page and rendered verbatim (every brand's homepage has small structural differences that a shared React block model can't absorb). Carolina Heating alone uses `page_type='home'`: a hand-built React homepage (blocks in `components/blocks/`, copy in the jsonb `data` column, shape `lib/db/homePageData.ts`) that predates the mirrored pipeline and is kept because it's verified and gets next/image treatment. Don't build React homepages for new brands.
4. **Every other page (`routes/mirrored-page.tsx`)** — served from the `pages` table via `getPage(routePath)`/`getAllPagePaths()` (`lib/db/pages.ts`), `dynamicParams = true` + `revalidate = 3600` (ISR: new/edited Supabase rows show up within an hour automatically, or instantly via `POST /api/revalidate`). Each row holds the page's `<main>` inner HTML (cleaned: WP Rocket lazy-load placeholders resolved, **`srcset`/`sizes` preserved** so browsers pick right-sized variants, absolute links made root-relative, schedule buttons given the brand's `scheduleUrl` as href, images pointing at Supabase Storage), plus `title`, `description`, `og_image_path`, and `inline_css` (WordPress' per-page `core-block-supports-inline-css` — `.wp-container-*`/`.wp-elements-*` rules whose hashes are unique per page, so they are emitted per page like WordPress does, not merged globally). `components/ThemeBehaviors.tsx` ports the theme's `carousel.js`, logo-carousel arrows, and lite-youtube click-to-play onto this server-rendered HTML. It also **upgrades every internal `<a href="/…">` inside mirrored HTML to a client-side navigation with viewport/hover prefetch** (the same behaviour as a Next `<Link>`); without that, each click inside mirrored content was a full page reload, which measured at several seconds to first paint versus ~100 ms client-side. `lib/mirroredHtml.ts` (`prepareMirroredHtml`) strips WordPress's leftover HTML comments and marks the first non-lazy image `fetchpriority="high"` at render time. The extractor (`npm run content:sync`) detects URLs that 301 on the live site (stale sitemap entries) and reports them for the `redirects` array instead of mirroring duplicate content.
5. **Images / fonts** — images live in Supabase Storage (public bucket `site-media`, path `<site_slug>/images/...`, resolved via `mediaUrl()` in `lib/supabase/server.ts`); fonts remain self-hosted in `public/fonts/`. Nothing hotlinks to the old site.
   - **Performance**: `next-config.mjs` (`createSiteConfig`) allows `next/image` to optimize the Supabase Storage hostname (computed from `SUPABASE_URL`). Every hand-built JSX `<img>` (Header/Footer logo, homepage hero/imagestack/promise images, `MaintenanceFinancing`, `OurCommunity`, `LogoCarousel`) uses `next/image` instead — this resizes + converts to a modern format + serves from Vercel's edge cache (e.g. the ~540KB header logo PNG becomes a ~17KB response at typical display size). The migration script also sets a 1-year `Cache-Control` on every Storage upload (`scripts/db/migrate-to-supabase.mjs`'s `uploadImages()`).
   - **Known gap**: the 106 mirrored pages' images are raw `<img>` tags inside `dangerouslySetInnerHTML`-injected WordPress HTML (`pages.html`), so they can't go through `next/image` without parsing/rewriting that HTML into React elements — a bigger, separate project. They still benefit from the long Storage `Cache-Control` and from `routes/layout.tsx`'s `<link rel="preconnect">` to the Supabase Storage origin, but not from resizing/format conversion. If this becomes a real bottleneck, the fix is either (a) post-process `content/html/*.json` at migration time to inject `srcset`/explicit dimensions, or (b) parse the HTML into React and swap `<img>` for `<Image>` at render time.
   - **Every `next/image` usage sets `placeholder="blur"` + `blurDataURL={shimmerDataUrl(w, h)}`** (`lib/imagePlaceholder.ts`) — a generic shimmer, not a real preview of the image (we don't have per-image blurhash data). This exists because Next.js's route prefetch on `<Link>` hover/viewport doesn't prefetch the actual (remote, on-demand-optimized) image bytes, so there's a real gap between a client-side navigation landing and the destination page's image finishing its fetch — worse on a cold Vercel image-optimizer cache. The shimmer fills that gap instead of leaving blank space. Add this to any new `next/image` usage.

## Data layer (Supabase)

- **Schema**: `supabase/schema.sql` (full) = migrations `0001_init` (core tables) + `0002_integrations` (nullable third-party IDs on `sites`) + `0003_multi_brand` (`header_tagline`, `license_lines`, `logo_width/height`, `source_origin`, `service_categories.icon`; `theme` jsonb = `{bodyClass, preloadFonts}`) + `0004_company` (`companies` table, `sites.company_id`/`status`, hot-path indexes, `brand_overview` view) — `sites`, `nav_items`, `service_categories`, `sub_services`, `locations`, `pages` (generic jsonb+html for mirrored/custom pages), `certifications`, `testimonials`, `redirects`, `media_assets`. Every content table carries `site_id` with an index and site-scoped unique constraints; Storage is namespaced `<slug>/...` in one bucket. RLS enabled everywhere, no permissive policies — all access is server-side via the `service_role` key (`lib/supabase/server.ts`, marked `server-only`). See `supabase/README.md` for full setup/onboarding steps for additional brands.
- **Query layer**: `lib/db/site.ts` (`getSite()`, React-`cache()`-wrapped) and `lib/db/pages.ts` (`getPage()`, `getAllPagePaths()`, `getSitemapEntries()`, `getSiteId()`). `lib/site.ts` now only exports TypeScript types (`SiteData`, etc.) — no runtime data. Never import a hardcoded site object; always go through `getSite()`.
- **Env vars** (see `.env.example`): `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `REVALIDATE_SECRET`. `SITE_SLUG` is NOT an env var — `createSiteConfig({ siteSlug })` in each brand's `next.config.ts` inlines it (env still overrides for local experiments). There is no middleware/proxy.
- **Seeding/re-syncing content**: `<brand>/content/` (`site.json`, `html/*.json`, `images/**`, optional `home.json`+`home-inline.css`) is the source-of-truth staging area fed into Supabase by `npm run db:migrate` (or `db:migrate:content-only` to skip re-uploading images). All scripts run from inside the brand folder, take the slug from `content/site.json`, and read the brand's `site.json` `source` block (`origin`, `imageHosts`, `urlRewrites`, `extraPages`, `locationSlugSuffix`). The migration is idempotent and only touches that brand's rows. It also derives a **thin index** into `locations` (pages ending in `source.locationSlugSuffix`) and `sub_services` (pages matching `/services/<category>/<sub-service>`) purely from mirrored-page paths — see "Locations & sub-services" below.
- **Editing content going forward**: either (a) edit the brand's `content/*` files and re-run `npm run db:migrate`, or (b) write directly to Supabase in a one-off script using the same pattern as `scripts/db/migrate-to-supabase.mjs`. After any edit, hit `POST /api/revalidate?secret=$REVALIDATE_SECRET&path=/some-path` for an instant refresh instead of waiting up to an hour for ISR.
- **Re-sync a page from the live WordPress site** → `npm run content:sync -- https://<origin>/<path>/`, then `npm run db:migrate`. Re-sync everything: `npm run content:pages` (rebuild `pages.txt` from sitemaps) → `npm run content:sync` → `npm run db:migrate`. Nav: `npm run content:nav -- --out <file>`.
- **Redirects** live in the `redirects` table (seeded from `<brand>/content/site.json`'s `"redirects"` array via `npm run db:migrate`) and are compiled into each deployment at **build time** by `createSiteConfig`'s `redirects()`, so the CDN answers them with no function invocation and no database round trip. There is deliberately no middleware/proxy on the request path — every request that isn't a cached page is a cost at 23-brand scale. Trade-off: a redirect added in Supabase takes effect on the next deploy; trigger one from the brand's Vercel **Deploy Hook**. Don't add hardcoded `redirects()` in a brand's `next.config.ts` — the table is the single source of truth.

### Locations & sub-services (thin index)

`locations` and `sub_services` have rich structured columns (`service_groups`, `faqs`, `since_categories`, etc.) designed for real field-level editing, but populating those requires actually parsing ~57 pages of freeform WordPress HTML into structured data — high effort, high risk of content drift from the live site. For now the migration script only inserts a **thin index** (slug/title/href/image, derived by pattern-matching `content/html/*.json` paths) into these tables for cross-linking/sitemap purposes. **The pages themselves still render from the generic `pages` table's mirrored HTML** (via `[...slug]/page.tsx`), not from these tables. If a brand later needs true structured editing of location/sub-service pages, that's a deliberate, separate project: extract each page's content into the structured columns and switch the relevant routes to render from `locations`/`sub_services` instead of `pages`.

## Third-party integrations

All of these are **nullable columns on `sites`** and render nothing when unset — safe by default for prototypes/staging. Fill in via Supabase (or `content/site.json`'s `business` object, re-run `npm run db:migrate`) when a brand actually goes live:

- **ServiceTitan scheduler** (`scheduler_id`, `scheduler_api_key`) — `routes/layout.tsx` conditionally renders the real `embed.scheduler.servicetitan.com/scheduler-v1.js` embed. `.se-widget-button` elements (see `Cta.tsx`'s `schedule` prop, `Header.tsx`) get a real click → `_scheduler.show(...)` via a delegated listener in `ThemeBehaviors.tsx` (reads the id from `<body data-scheduler-id>`), falling back to their normal href (the `/bookings` mirrored page) if the widget/id isn't configured.
- **Google Tag Manager** (`gtm_id`) and **Tealium** (`tealium_src`) — raw snippets in `layout.tsx` (not `@next/third-parties/google`, which currently only ships versions tracking Next's 16.4 canary line — revisit once it has a stable release matching our Next version).
- **Cookie consent banner** (`components/CookieConsent.tsx`) — renders whenever the company's `cookie_notice_html` is set (no third-party dependency; it's the NearU theme's own `cookie-consent.js` custom element, faithfully ported as a client component using the exact same tag/classes so theme.css's `cookie-consent[module-type=banner]` rules apply unchanged). Cookie name/expiry (`cookieConsent_acknowledged`, 7 days) matches the original.
- **Structured data (JSON-LD)** — `layout.tsx` emits site-wide Organization/LocalBusiness/WebSite (matching the live site's AIOSEO `@graph`); `lib/schema.ts`'s `buildPageSchema()` adds per-page WebPage/BreadcrumbList, used by both `page.tsx` and `[...slug]/page.tsx`.
- **Chat widget** ("Text us" bubble) — still not ported; no embed code/account id captured yet.
- The generator landing page's Mailchimp form posts directly to Mailchimp and works without extra JS.

## Performance model

- **Static + edge-cached**: every page is prerendered at build (`generateStaticParams`) with ISR (`revalidate = 3600`, `dynamicParams = true`); Vercel serves them from the CDN (`x-vercel-cache: HIT`, ~100 ms TTFB). No database is touched while a visitor browses.
- **Entry visit**: `experimental.inlineCss` inlines the ~220 KB theme stylesheet into the HTML (≈30 KB compressed), removing the render-blocking CSS round trip — the equivalent of WP Rocket's inlined "used CSS" on the live sites. The hero image gets `fetchpriority="high"`.
- **Every subsequent click**: client-side navigation + prefetch, whether the link is a React `<Link>` or a plain anchor inside mirrored WordPress HTML (see ThemeBehaviors). Back/forward use bfcache.
- **No request-path functions**: redirects are compiled at build; there is no middleware/proxy.
- When measuring, compare like with like: the live WordPress sites sit behind Cloudflare + WP Rocket page cache with inlined critical CSS, so an "H1 visible" stopwatch on a cold hard-load is their best case. The new sites should match that on entry and beat it decisively on every navigation after.

## SEO infrastructure

- `routes/sitemap.ts` — one flat sitemap generated from `getSitemapEntries()` (every `pages` row for this site). Replaces the live site's 3-file AIOSEO sitemap index; fine for a single-brand site well under the 50k-URL limit.
- `routes/robots.ts` — allows all, points at `/sitemap.xml`.
- `routes/not-found.tsx` — themed 404 (uses `getSite()` for phone number + top service links).
- `routes/error.tsx` — themed error boundary for errors in pages/children of the root layout. Must be a Client Component (Next.js requirement) so it can't call `getSite()`.
- `routes/global-error.tsx` — last-resort boundary for errors in the **root layout itself** (e.g. Supabase totally unreachable during `getSite()` in `layout.tsx`) — `error.tsx` can't catch those since a layout's errors can only be caught by replacing the whole document. Deliberately plain/inline-styled, no theme.css dependency.

## Verification tools

- `node scripts/screenshot.mjs <url> <out.png> [w] [h] [waitMs] [clickSelector]` — full-page (or click-then-viewport) screenshot via Chrome DevTools Protocol. Use it to compare `http://localhost:3000/<path>` against `https://carolinaheating.com/<path>/`.
- `node scripts/eval.mjs <url> "<js expression>"` — evaluate JS (e.g. computed styles, or check client-rendered elements like `<cookie-consent>`) in the rendered page.
- Note: the live site delays all JS until user interaction (WP Rocket), so headless screenshots of it lack the yellow banner, carousel chrome, and video poster. Those are present in a real browser and in our build.

## Do not

- Do not add Tailwind or other CSS frameworks — the theme CSS ships its own reset and grid primitives and they conflict.
- Do not hotlink images/fonts to carolinaheating.com — Cloudflare bot protection on that origin blocks Vercel's image optimizer.
- Do not import `lib/supabase/server.ts` (or anything from `lib/db/*`) into a `"use client"` file — it's `server-only` and uses the service-role key on purpose. Client components that need site data should receive it as props from a server component ancestor (see `Header.tsx` / `GoogleReviews.tsx` + `GoogleReviewsSection.tsx` for the pattern).
- Do not hardcode this brand's business info/copy/nav in component code — it belongs in Supabase (`sites`/`nav_items`/etc.) so the same components work for all 23 brands. Add new fields to the schema + `SiteData` type instead of hardcoding.
- Do not add a hardcoded `redirects()` to `next.config.ts` — see "Redirects" above.
- Do not render a real custom element tag in JSX (e.g. `<cookie-consent>`, `<lite-youtube>`) without adding it to `types/custom-elements.d.ts` first — React 19 doesn't type-check unknown hyphenated tags automatically, and the augmentation must target `declare module "react" { namespace JSX {...} }`, **not** `declare global { namespace JSX {...} }` (the latter silently fails to merge under `"jsx": "react-jsx"`).
